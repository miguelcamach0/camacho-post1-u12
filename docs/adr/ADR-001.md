# ADR-001: Arquitectura en capas simples para persistencia y conservación del mecanismo Observer para notificaciones

## Estado

**Aceptado — 2026-11-11**

## Contexto

El Sistema de Solicitudes de Reembolso de Gastos Corporativos integra tres patrones de diseño que resuelven necesidades funcionales independientes:

- **Chain of Responsibility:** ejecuta las verificaciones de documentos soporte, monto máximo y solicitudes duplicadas.
- **Strategy:** selecciona la fórmula de cálculo correspondiente a cada categoría de gasto.
- **Observer:** notifica los cambios de estado a empleados, Contabilidad y Auditoría.

El sistema utiliza una organización en capas que separa el dominio, el procesamiento, la aplicación, la infraestructura y los adaptadores REST.

Actualmente, `SolicitudReembolsoService` coordina los tres patrones y depende directamente de `RepositorioSolicitudesJpa`, que extiende `JpaRepository<SolicitudReembolso, Long>`.

La persistencia utiliza Spring Data JPA y una base de datos H2 en memoria. No existe un plan documentado para sustituir el motor de base de datos ni se ha identificado una segunda implementación de persistencia necesaria.

Por otra parte, el servicio utiliza `List<ObservadorCambioEstado>` para comunicar los cambios de estado a las implementaciones registradas en Spring. Esta interfaz permite desacoplar el servicio de los notificadores concretos.

El área de Contabilidad anunció una futura integración con una API externa para gestionar los pagos de solicitudes aprobadas durante el próximo trimestre.

La Guía de la Unidad 12 propone considerar una arquitectura Hexagonal completa cuando existan expectativas de mantenimiento prolongado, de tres años o más, acompañadas de cambios de infraestructura.

En el proyecto actual no se cuenta con evidencia suficiente de una necesidad de sustitución de la persistencia durante ese horizonte. En cambio, sí existe un cambio anunciado para las notificaciones, pero el diseño actual ya dispone de un punto de extensión adecuado.

Por lo tanto, resulta necesario evaluar si introducir nuevos puertos e interfaces aportaría beneficios reales o constituiría sobreingeniería.

## Alternativas evaluadas

### Alternativa 1: Migrar completamente a arquitectura Hexagonal

Esta alternativa consiste en crear una interfaz `RepositorioSolicitudes` que actúe como puerto de persistencia y una implementación adaptadora basada en JPA.

Adicionalmente, podrían introducirse nuevas interfaces y adaptadores específicos para los mecanismos de notificación externos.

**Ventajas:** ofrece mayor independencia de los detalles de infraestructura y facilita sustituir determinadas implementaciones cuando exista esa necesidad.

**Desventajas:** incrementa el número de interfaces, clases, adaptadores y responsabilidades que deben mantenerse. En el contexto actual, una parte de estas abstracciones no responde a variaciones documentadas.

### Alternativa 2: Mantener capas simples y aprovechar las abstracciones existentes

Esta alternativa conserva la dependencia directa del servicio hacia el repositorio JPA y mantiene la interfaz `ObservadorCambioEstado` para las notificaciones.

**Ventajas:** reduce la complejidad, conserva la claridad del diseño y aprovecha las extensiones que ya fueron justificadas por los requisitos funcionales.

**Desventajas:** la persistencia permanece acoplada a Spring Data JPA y, ante un cambio significativo de tecnología o estrategia de almacenamiento, podría requerirse una refactorización.

## Decisión

**Se adopta la alternativa 2: mantener una arquitectura en capas simples para la persistencia y conservar el punto de extensión actual de las notificaciones.**

### Decisión sobre persistencia

`SolicitudReembolsoService` continuará dependiendo directamente de `RepositorioSolicitudesJpa`.

No se creará una interfaz adicional `RepositorioSolicitudes` ni un adaptador intermedio, debido a que no existe actualmente una necesidad demostrada de reemplazar el mecanismo de persistencia.

Introducir ese puerto representaría una abstracción especulativa que aumentaría el mantenimiento sin resolver un problema presente.

Esta elección aplica el principio YAGNI y mantiene una estructura acorde con la complejidad actual del sistema.

### Decisión sobre notificaciones

Se conservará la interfaz `ObservadorCambioEstado` y sus implementaciones existentes.

No se introducirá un segundo mecanismo de abstracción ni se migrará el módulo completo a una arquitectura Hexagonal.

La integración futura con la API externa de Contabilidad podrá desarrollarse mediante la modificación o sustitución de la implementación de `NotificadorContabilidad`, respetando el contrato `ObservadorCambioEstado`.

De esta manera, `SolicitudReembolsoService` podrá continuar notificando a los interesados sin depender de los detalles de comunicación con la API externa.

La incorporación de una API real requerirá evaluar aspectos adicionales, como manejo de errores de comunicación, tiempos de espera, reintentos e idempotencia, antes de su puesta en producción.

## Justificación técnica

La decisión se fundamenta en los principios YAGNI, KISS y responsabilidad única.

**YAGNI:** no se implementarán interfaces de persistencia adicionales sin una necesidad real de sustitución tecnológica.

**KISS:** se conservará una arquitectura sencilla, comprensible y suficiente para las funcionalidades actuales.

**Responsabilidad única:** cada clase mantendrá su función específica, separando validación, cálculo, notificación, coordinación y persistencia.

El criterio de mantenimiento prolongado con cambios de infraestructura se evalúa individualmente para cada dependencia.

En persistencia no existe una variación documentada que justifique un puerto adicional.

En notificaciones sí se conoce una integración próxima, pero la variabilidad ya está encapsulada mediante la interfaz Observer.

Por lo tanto, la asimetría entre la persistencia y la notificación es una decisión consciente basada en necesidades distintas y no una inconsistencia accidental.

## Consecuencias

### Consecuencias positivas

1. Se evita introducir interfaces y adaptadores de persistencia sin un caso de uso que los justifique.
2. Se conserva una estructura de código sencilla, con responsabilidades diferenciadas.
3. Se reduce el costo de implementación y mantenimiento de abstracciones innecesarias.
4. La futura integración externa de Contabilidad puede aprovechar la interfaz `ObservadorCambioEstado` existente.
5. El servicio principal no necesita conocer los detalles concretos de cada notificador.
6. La decisión mantiene coherencia con los principios YAGNI y KISS.

### Consecuencias negativas

1. El servicio de aplicación mantiene una dependencia directa de Spring Data JPA.
2. Si en el futuro se requiere reemplazar la estrategia de persistencia, podría ser necesario introducir un puerto y refactorizar el servicio.
3. La arquitectura no mantiene una separación simétrica de todas las dependencias externas, lo que requiere una justificación explícita.
4. El mecanismo actual de notificación es síncrono; una futura integración externa podría introducir fallos de red o demoras que afecten la respuesta del servicio.
5. Guardar una solicitud y después ejecutar una notificación externa no garantiza, por sí solo, la consistencia entre la operación de base de datos y el sistema externo.

Estas consecuencias se aceptan conscientemente en el alcance actual del proyecto.

## Condiciones para reconsiderar la decisión

La decisión podrá revisarse si ocurre alguna de las siguientes situaciones:

- Se documenta la necesidad de incorporar otro mecanismo de persistencia o sustituir el actual.
- El sistema requiere múltiples implementaciones de almacenamiento utilizadas por distintos entornos o casos de uso.
- La evolución del proyecto demuestra una necesidad sostenida de aislar la persistencia del servicio de aplicación.
- La integración de Contabilidad exige garantías adicionales de entrega, tolerancia a fallos o procesamiento asíncrono que no puedan resolverse adecuadamente con el mecanismo actual.
- Surgen nuevos requisitos de infraestructura que justifiquen abstraer dependencias adicionales.

La decisión no impide una evolución arquitectónica futura. Establece que las abstracciones deben incorporarse cuando exista evidencia concreta que las justifique.

## Conclusión

Se determina que el Sistema de Solicitudes de Reembolso de Gastos Corporativos no requiere actualmente una migración completa a arquitectura Hexagonal.

La persistencia continuará utilizando una dependencia directa hacia Spring Data JPA, mientras que las notificaciones conservarán la interfaz `ObservadorCambioEstado` como mecanismo de extensión.

Esta solución permite responder a las necesidades presentes, preparar la integración externa conocida y evitar sobreingeniería.

La arquitectura podrá evolucionar cuando aparezcan nuevas necesidades técnicas verificables.
